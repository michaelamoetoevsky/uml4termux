# Direction N1–N4 — the four phases after the queue

Companion to the wayfinder map ([issue #1](https://github.com/michaelamoetoevsky/uml4termux/issues/1)).
Every phase has an **entry condition**, an **exit criterion** that a command can check, and the
ticket that carries it. Nothing here is "done" because it was written down; each exit criterion
is a measurement, and the phase is only marked complete when that measurement is in the repo.

Why these four and not others: the packaging gate closes on **2026-12-24** or at **10 stars**
(`docs/ADOPTION.md`), so adoption work has a deadline that engineering does not. The technical
work is worth doing in parallel but must not multiply: **one axis at a time** (N4), chosen
against measured numbers rather than interest.

---

## N1 — Visible: someone can see it work without installing it

**Entry:** none (starts now).
**Exit:** an artifact in the repository that shows a real run — commands, timings and actual
output captured from a device — plus a link to it from the README's first screen.

| Work | Evidence it is done |
|---|---|
| Run the documented demo on the device and capture it | `docs/DEMO.md` generated by `bench/demo-capture.sh`, containing the real output and per-step wall time |
| A watchable recording | attempted and either present as a file, or its failure recorded with the exact error — no "would be nice" |
| README points at it | first screen links `docs/DEMO.md`; link check passes |

**Not in scope:** editing, music, subtitles, publishing to a video platform (that is the
owner's call, and it is an external action).

**Ticket:** #5.

## N2 — Used by someone else: the first external signal

**Entry:** N1's artifact exists (a person needs something to look at).
**Exit:** one of these, from an account other than the author — an issue describing a run, a
discussion, or a merged external PR.

| Work | Evidence |
|---|---|
| Answer Docker-on-Termux questions where they are asked, linking the repo only when it answers the question | the thread URL recorded in the ticket |
| Label contributor-sized work (second initramfs base, glibc packaging path, `proot-distro` comparison notes) | ≥1 issue labelled `good first issue` with a written acceptance test |

**Why this cannot be faked, and is not:** `docs/ADOPTION.md` §"What this project will not do".
A manufactured star or a sockpuppet issue is disprovable and would poison every later
submission.

**Ticket:** new (#7), because #2 answered *what* to expect and this one is the doing.

## N3 — Resubmitted: the package reaches a human

**Entry (either):** 10 stars, **or** `age_days ≥ 60` — i.e. **2026-12-24**.
**Exit:** the PR is open and **not** auto-closed by `check-new-package-source`, with the linter
output attached.

| Work | Evidence |
|---|---|
| Re-check the three gate inputs | `bench/adoption-report.py` output pasted into the ticket |
| Branch from the **upstream** `master` sha | the branch's parent sha equals `GET /repos/termux/termux-packages/git/ref/heads/master` |
| Re-run their linter | `Everything seems ok.` (15 checks) attached |
| Enable maintainer edits on the fork | the bot's warning does not appear |

**Ticket:** #6 (blocked on the entry condition, which is a date or a number — not a judgement).

## N4 — One technical axis, chosen by measurement

**Entry:** a measurement that says which axis pays. Baseline in hand: container start is
**15 740 ms** median in the quiet run and **26 086 ms** under load (`docs/ADOPTION.md`,
`evidence/20261031-registry-numbers.json`), which is a 10 s spread nobody has explained.
**Exit:** one axis written into the map as the decision, with a number it promises to move and
the method that would show it moved.

### N4's first measurement is in (2026-11-01, `evidence/boot-20261031-timeline.json`)

Three captures of the same boot, with the console stamped line by line (`bench/console-stamp.py`):

| Phase | This device, one boot |
|---|---|
| kernel up (first console line) | **5.1–13.1 s** |
| initramfs → guest script | **0.1–7.1 s** |
| guest script → dockerd answering | **0.4–0.8 s** |
| first container after that | **0.1–0.7 s** |
| teardown (`down`) | **3.0 s** (was 22.8 s before the stop-path fix) |

The spread is not noise to be averaged away: the guest's own startup script pulls images at
boot, and a capture taken while it was pulling measured 178 s for the same sequence. That is the
real answer to "why does a container start take 15–26 s" — **it is not the container, and not
dockerd** (0.4 s), it is boot plus whatever the guest decides to fetch.

| Candidate axis | The number it would move | Cost |
|---|---|---|
| Container-start latency | 15–26 s → under 10 s would change how the tool feels | requires a phase breakdown first (where do the seconds go: kernel boot, dockerd, image unpack?) |
| Kernel upstream (PR #26, mailing list) | not a number — institutional risk | low code, high patience |
| Features (snapshot UX, panel actions) | user-visible capability | does not fix the 26 s |

**Rule:** the phase breakdown comes **before** the choice. Choosing "performance" without
knowing which second is expensive is the most common way a month disappears.

**Ticket:** #4 (the decision), and its first deliverable is the breakdown, not the fix.

---

## Order and overlap

```
N1 ──► N2 ──► N3        (N3 also opens by itself on 2026-12-24)
        │
        └─ N4 runs in parallel, one axis, starting from the phase breakdown
```

N4 may not start a second axis until the first has either moved its number or been abandoned
with the measurement that justified abandoning it.
